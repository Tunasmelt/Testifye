# Feature 9: i18n / RTL Audit
Phase: 4 | Pipeline: Scout → Generator → Judge

## What it does
Checks UI for internationalization readiness. Flags truncated text risks, RTL layout issues, hardcoded strings, date/number format assumptions, and cultural tone mismatches.

## Key files
- `src/app/api/generate/i18n-audit/route.ts`
- `src/lib/schemas/i18n-audit.ts` — I18nAuditOutputSchema (see SCHEMA.md)
- `src/components/features/I18nAuditPage.tsx`
- `src/components/generation/I18nFindingCard.tsx`

## Output fields (from SCHEMA.md I18nAuditOutputSchema)
```
readiness_score:    0–100  (100 = fully i18n-ready)
target_locales:     string[]  (user-selected or auto-detected from project context)
findings[]:
  category:         text_truncation | rtl_layout | hardcoded_string
                    | date_format | number_format | cultural_tone
  severity:         critical | high | medium | low
  screen:           string
  element:          string
  description:      string
  fix_example:      string  (code or design suggestion)
rtl_risk_score:     0–100  (100 = completely breaks in RTL)
hardcoded_strings:  string[]  (UI text that should be in i18n keys)
summary:            string
```

## Categories
| Category | Examples |
|---|---|
| text_truncation | Labels that will overflow in German/Arabic (longer than English) |
| rtl_layout | Left-aligned flows that break in Arabic/Hebrew RTL |
| hardcoded_string | English text in JSX that should be `t('key')` |
| date_format | "12/05/2025" is ambiguous — MM/DD vs DD/MM |
| number_format | "$1,234.56" — comma/period meaning differs by locale |
| cultural_tone | Idioms, humor, or cultural references that don't translate |

## readiness_score calculation (in Judge prompt)
- Start: 100
- Each critical finding: -15
- Each high finding: -8
- Each medium finding: -3
- Each low finding: -1
- Floor at 0

## Gotchas
- `readiness_score` is a new field (from gap analysis) — include it in Judge verification
- `rtl_risk_score` is separate from `readiness_score` — a UI can be i18n-ready but still RTL-broken
- `hardcoded_strings` are extracted by Scout from ScreenElementMap text labels — not generated by AI
- `fix_example` should be a concrete code snippet or design mockup suggestion, not vague advice
